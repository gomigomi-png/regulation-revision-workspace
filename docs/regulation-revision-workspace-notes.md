# 規程改正ワークスペース 検討メモ

このメモは、規程改正ワークスペースの**設計判断**（目的・方針・ペイン責務）の正本である。

ファイルのありか、開き方、GitHub 作業手順は [regulation-revision-workspace-guide.md](regulation-revision-workspace-guide.md) を見る。
画面・データ・出力の流れは [regulation-revision-visual-explainer.md](regulation-revision-visual-explainer.md) を見る。

## 目的

既存の4ペインひな形をもとに、会社規程の改正作業に使うワークスペースを作る。

主な目的は、規程改正案を常務会に提案するときの資料作成を支援すること。

作成したいアウトプット:

- 改正規程文
  - 規程全文の中で、改正箇所が赤字下線表示されたもの
  - Wordファイルとして出力したい
- 新旧対照表
  - 改正後の文と改正前の文を左右に配置したもの
  - Wordファイルとして出力したい
- 修正履歴
  - どの規程のどの条文を、どのように修正したかを残したい

## 固定した方針

### 外部AIには出さない

社内規程を扱うため、規程本文をいきなり外部AIに送る設計にはしない。

初回版では、外部AIによる自動解析や自動修正ではなく、人間が確認・整形する前提にする。

### Word自動読み込みは初回スコープ外

最初の版では、Wordファイルをアップロードして自動解析する方式にはしない。

代わりに、人間がWord本文をコピーして画面に貼り付ける。

理由:

- 会社規程のWordは書式・表・インデント・別表などのばらつきが大きい
- Wordファイルを正確に解析する機能は難易度が高い
- 今回は初めての開発であり、難易度を上げすぎないことを優先する

### ワークスペース単位

1つの改正案件に対して、複数の規程を扱えるワークスペースにする。

例:

- 看護休暇日数の変更
  - 就業規則
  - 育児介護休業規程
  - パートタイマー就業規則

理想形としては、将来的に規程マスタから影響規程・影響箇所を抽出したい。

ただし初回版では、対象規程と対象条文は人間が追加する。

### 対象規程・対象条文の抽出は自動化しない

「看護休暇」に関係する規程や条文を、アプリが自動で探す機能は初回スコープ外。

初回版では、人間が対象規程を追加し、本文を貼り付ける。

理由:

- 影響箇所の自動抽出には、規程マスタ、検索精度、法務判断が絡む
- 常務会資料作成という今回の目的には必須ではない
- まずは資料作成に直結する機能を優先する

### 規程全文を扱う

当初は「修正対象条文だけ」を扱う案も検討した。

しかし、常務会提出用の新規程案は「規程全文に修正箇所が赤字下線で入ったもの」であるため、アプリ内で規程全文を持つ方針に切り替えた。

理由:

- 修正対象条文だけを扱うと、最終的な全文版を作るために、人間が旧規程全文へ修正条文を貼り戻す作業が残る
- 規程全文を持てば、アプリから改正規程文を出力しやすい

### 条文候補への分割

全文貼り付け後、アプリがローカルの単純ルールで条文候補に分割し、人間が修正する方式にする。

イメージ:

1. 人間がWord本文を画面に貼り付ける
2. アプリが「第○条」を目印に、ローカル処理でざっくり条文単位に分ける
3. 人間が分割結果を確認し、必要ならタイトル・本文を修正する
4. 条文単位で旧文・新文・差分・履歴を管理する

「条文候補」とは、アプリが作った下書きの区切り。

会社規程には、附則、別表、様式、表などの例外があるため、単純ルールだけで完全に分割する前提にはしない。

初回版では、結合・分割の高度な編集よりも、以下を優先する。

- タイトル修正
- 本文修正
- 条文の新設
- 条文の削除状態

条文の削除は、条文データ自体をすぐ消すのではなく、「削除」状態または新文なしとして扱う。
条文の新設は、旧文なし・新文ありの条文として追加する。

条番号の繰り上げや新設に伴う番号調整は、初回版ではアプリが自動で振り直さず、人間が新文側を編集する。

## 4ペインの責務（確定版）

規程改正ワークスペースでは、4ペインを以下の役割で固定する。

このワークスペースでは、既存のワークスペース設計ルールとは異なり、Pane 3 を編集画面にする。
理由は、規程改正作業では「条文を選び、旧文を見ながら新文を直す」ことが中心作業になるため。

4ペインの直感的な役割:

- Pane 1: どの規程を直すか
- Pane 2: どの条文を直すか
- Pane 3: どう直すか
- Pane 4: 直した結果どう見えるか

### Pane 1: 改正案件内の対象規程リスト

複数の対象規程を並べる。

表示するもの:

- 規程名
- 進捗ステータス

進捗ステータスは、初回版では以下の3段階に絞る。

- 未着手
- 編集中
- 確認済み

「完了」は、確認済みと運用が被りやすいため初回版では入れない。

### Pane 2: 選択中規程の全条文リスト

選択中の規程について、全文の全条文を並べる。

条文リストでは、以下の2種類を分けて表示する。

- 修正対象
  - 人間が「今回直す予定」と指定した条文
- 差分あり
  - アプリが「旧文と新文が違う」と検出した条文

初回版では、修正対象条文だけのリストにはしない。

### Pane 3: 選択中条文の編集画面

選択した条文を編集する領域。

Pane 3 は、旧文を固定表示し、新文だけを編集する。

理由:

- 旧文を誤って変更する事故を避けられる
- 新旧対照表を安定して作れる
- 赤字下線差分プレビューを作りやすい

Pane 3 に置くもの:

- 旧文
  - 固定表示
- 新文
  - 編集可能
- 修正理由
  - 編集可能
- 修正対象指定
  - 必要に応じて操作できるようにする

### Pane 4: 差分・チェックの補助パネル

Pane 4 は、赤字下線差分プレビューを主役にする。

初回版では、選択中の条文だけを対象に赤字下線差分プレビューを表示する。

Pane 4 の補助候補:

- 新旧対照表プレビュー
- 修正履歴
- チェック結果

ただし初回版では、Pane 3 で新文を編集しながら、Pane 4 で選択中条文の差分をすぐ確認できることを優先する。

出力機能は Pane 4 に常駐させない。
新旧対照表 Word 出力や改正後全文テキストコピーは、選択中条文ではなく規程全体に関わる操作であるため、画面上部または規程単位のアクションとして扱う。

## 出力方針

### 新旧対照表 Word 出力を優先する

初回版の正式なWord出力は、新旧対照表を優先する。

参考資料 `docs/shinkyutaisyou-ex.pdf` の形式を踏まえ、常務会提出用の出力は以下の形に寄せる。

- 見出し
  - 修正対象規程のタイトルを表示する
- 列
  - 左: 新
  - 右: 旧
- 変更のない範囲
  - `第1条～第2条 【略】` のように省略して表示する
- 修正理由
  - 常務会提出用の新旧対照表には出さない
  - アプリ内部の管理情報、履歴、確認用として保持する
- 末尾
  - 必要に応じて `以上` を表示する

### 赤字下線入り改正規程全文への補助

赤字下線入りの改正規程全文も最終的には必要だが、初回版では完全自動生成までは狙わない。

代わりに、人間がWordで作りやすくするため、以下を用意する。

- 改正後全文テキストのコピー
  - 各条文の新文を規程順に並べた下書き
  - 削除条文は除外し、新設条文は指定位置に入れる
- 修正条文一覧
  - どの条文をWord上で赤字下線にすべきか確認できる一覧
- 条文別の赤字下線プレビュー
  - Pane 4 で選択中条文について確認する

これにより、人間は既存の旧規程Wordを開き、修正条文一覧とPane 4の差分を見ながら、赤字下線入りの改正規程全文を作成できる。

## データモデル仮型

初回実装では、データモデルを以下の単位に分ける。

- 改正案件
  - 1つの常務会提案テーマ、または1つの改正作業単位
  - 複数の対象規程を持つ
- 対象規程
  - 規程名、進捗ステータス、貼り付け元の全文、条文ブロック一覧を持つ
- 条文ブロック
  - 規程内の表示順を持つ最小編集単位
  - `第○章`、`第○条`、`附則`、`別表` などを同じ配列で扱う
  - 旧文と新文を分けて持つ

実装上の仮型は `lib/regulation-revision/schema.ts` に置く。

```ts
type RegulationRevisionWorkspace = {
  id: string;
  title: string;
  status: "draft" | "reviewing" | "readyForSubmission";
  summary: string;
  regulations: RevisionRegulation[];
};

type RevisionRegulation = {
  id: string;
  title: string;
  progressStatus: "notStarted" | "editing" | "confirmed";
  sourceText: string;
  articles: RegulationArticleBlock[];
};

type RegulationArticleBlock = {
  id: string;
  order: number;
  kind: "chapter" | "article" | "supplementary" | "appendix" | "form" | "other";
  label: string;
  title: string;
  oldText: string | null;
  newText: string | null;
  revisionReason: string;
  isRevisionTarget: boolean;
};
```

### 保存する状態と派生する状態

保存する状態:

- 人間が入力した案件名、規程名、本文、修正理由
- 人間が指定した修正対象フラグ
- 条文ブロックの順序
- 旧文・新文の有無

派生する状態:

- 差分あり
  - `oldText` と `newText` が異なるかどうかで判定する
- 変更種別
  - `oldText` あり・`newText` あり・内容差分なし: 変更なし
  - `oldText` あり・`newText` あり・内容差分あり: 通常修正
  - `oldText` なし・`newText` あり: 新設
  - `oldText` あり・`newText` なし: 削除

`差分あり` や `通常修正` は保存せず、出力・表示の直前に派生計算する。

### 出力に必要な派生データ

新旧対照表 Word 出力では、対象規程ごとに以下を作る。

- 変更のある条文行
  - 条文ラベル
  - 見出し
  - 新文
  - 旧文
  - 変更種別
- 変更のない範囲の省略行
  - 開始条文ラベル
  - 終了条文ラベル

改正後全文テキストコピーでは、規程内の `articles` を `order` 順に並べ、`newText` を連結する。
削除条文は `newText` がないため除外し、新設条文は `order` の位置に入る。

## 将来機能として残すもの

初回版では扱わず、将来検討するもの:

- Wordファイルの自動読み込み
- 規程マスタから影響規程・影響箇所を自動抽出する機能
- 外部AIによる誤字脱字チェックや規程作成ルールチェック
- 共同編集
- 承認ワークフロー
- 厳密な監査ログ

ただし、外部AIに出さずにできる範囲で、ローカルの単純チェックを追加する余地はある。

例:

- 条番号の抜けや重複チェック
- 「第○条」形式の表記ゆれチェック
- 修正対象条文に修正理由が入っているかのチェック

## 次回の開始点

次回は、データモデルと初回実装範囲の整理から再開する。

再開時に検討すること:

- 規程・条文・修正状態のデータ構造
- 新旧対照表Word出力に必要な情報
- 改正後全文テキストコピーに必要な情報
- 画面上で最初に作るべき操作フロー
